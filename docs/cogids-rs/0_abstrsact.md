# CogiDS-rs 詳細設計書

CogiDS-rs は Rust で書かれたニンテンドーDS エミュレータです。この文書は、ソースを初めて読む人が「どこに何があり、1フレームがどう流れるか」をつかめるように、全体の構成と主な処理の流れをまとめたものです。

- 対象：`core/*`（エミュレータ本体）と `gui/*`（フロントエンド）
- 細かい仕様は各ソースの先頭コメント（`//!`）に図つきで書かれています。この文書は、その入口として使ってください。
- ハードウェアの仕様は GBATEK に、移植元の実装は CorgiDS / melonDS に従っています。

## 2. エミュレーションの中核（`ds_emu`）

### 2.1 1フレームの流れ

`Emulator::run()`（`core/system/src/emulator/runner.rs`）は、DS の1フレーム（263 ライン、バス 560190 サイクル）を実行します。2つの CPU と周辺機器を小さな時間単位で交互に進める「キャッチアップ方式」です。

```text
run()
 1. gpu.start_frame()      フレーム完了フラグを下ろす
    wifi.new_frame()       通信リンクの送受信を進める
    run_cheats()           Action Replay コードを適用
 2. 192 ライン目で VBlank に入るまで繰り返す
    a. calculate_system_timestamp()   次の区切り（最大 64 サイクル、または次のイベント）
    b. ARM9 (66MHz)：system_timestamp×2 に追いつくまで
         execute → タイマ9 → 3D エンジン
    c. ARM7 (33MHz)：system_timestamp に追いつくまで
         execute → タイマ7 → SPU
    d. Wi-Fi を進め、割り込みを上げる
    e. GPU イベント（HBlank / VBlank / ライン）
    f. DMA イベント
    g. カートリッジの転送
 3. cart.save_check()       落ち着いたら .sav を書き出す
```

呼び出し側は `run()` のあと、`get_upper_frame` / `get_lower_frame` で画面を、`take_audio_samples` で音声を受け取ります。

**ポイント：** ARM9 のタイムスタンプは 66MHz 単位です。差分ではなく両方を半分にしてから引きます。`cycles_ran() >> 1` だと1サイクルの命令が 0 に丸められ、GXSTAT やタイマを待つループで 3D やタイマが進まなくなるためです（ある市販ソフトで実際に止まった例があります）。

### 2.2 命令の実行

`execute(cpu)` は1命令を実行します。HALT 中や DMA でバスがふさがっているときは、時刻を区切りまで進めて割り込みだけを確認します。命令は `read_*` / `write_*`（`emulator/read`, `emulator/write`）を通じて各デバイスへアクセスします。ARM9 用と ARM7 用でアドレスの対応表が分かれています。

### 2.3 その他の構成要素

| 要素 | 場所 | 内容 |
|---|---|---|
| DMA | `emulator/dma.rs`, `dma.rs` | 即時・VBlank・HBlank・カード転送のタイミング |
| 割り込み | `emulator/interrupt.rs` + `ds_interrupt` | IE/IF/IME、HALT からの復帰 |
| 3D 実行 | `emulator/gpu/gpu_3d.rs` | GX FIFO とコマンドの実行を CPU 時間に合わせて進める |
| 音 | `emulator/sound.rs` | SPU を ARM7 の時間で進め、サンプルをためる |
| チート | `emulator/cheats.rs` | melonDS `AREngine.cpp` の移植。`parse_ar_code` で文字列から変換 |
| ロード | `emulator/load.rs` | ROM 読み込み、BIOS/ファームウェアの準備、ダイレクトブート |

## 3. 映像（`ds_gpu`）

### 3.1 構成

```text
 CPU バス → io.rs（レジスタ） / memory.rs（パレット・OAM・VRAM）
                 │
   vram.rs：バンク A〜I を BG / OBJ / テクスチャ / LCDC に割り当て
                 │
   ┌─────────────┴──────────────┐
 engine_3d/                     engine_2d/（エンジン A：BG0 に 3D を表示可）
  geometry → raster ─────────→  engine_2d/（エンジン B）
                                      │
                                display/：画面出力、上下入れ替え、輝度
```

- **2D エンジン**（`engine_2d/`）：ラインごとに BG（`bg.rs`）と OBJ（`obj.rs`）を描き、`compose.rs` でウィンドウや半透明・輝度効果を合成します。
- **3D ジオメトリ**（`engine_3d/geometry/`）：GX コマンドを実行します（行列スタック、ライティング、クリッピング、ポリゴン化）。
- **3D ラスタライザ**（`engine_3d/raster/`）：melonDS のソフトウェアレンダラの移植です。エッジの傾き、パースペクティブ補正、深度テスト、半透明・影のポリゴン ID 規則、エッジマーキング、フォグ、アンチエイリアスを再現します。

### 3.2 3D ラスタライザの並列化

フレーム全体を横帯（バンド）に分け、[rayon](https://crates.io/crates/rayon) のスレッドプールで並列に描きます（`raster/mod.rs` の `render_frame`）。

```text
render_frame()
 1. clear_borders()         画面外の上下1行（エッジマーキングが参照）だけを消去
 2. バンドごとに並列（rayon）
      Band::load()          自分の行の layer0 を clear_rows() で消去（または背景ビットマップ）
                            layer1 は元のバッファからコピー
      Band::render()        バンドに掛かるポリゴンを集め、先頭行でエッジを設定して各行を描く
      Band::final_pass()    上下の行がバンド内にある行のエッジマーキング・フォグ・AA
      Band::store()         自分の担当範囲（他バンドと重ならない）へ書き戻す
 3. 各バンドの先頭行と最終行の final pass（上下のバンドの結果が必要なため最後に行う）
```

- バンド数：等倍は CPU 数（最大 8）、高解像度は CPU 数×2（最大 32）です。ポリゴンが一部に集中しても、空いたスレッドが次のバンドを処理できます。
- final pass が隣の行から読むのは、ポリゴン ID（attr の上位ビット）と深度だけです。どちらも final pass では変わらないので、行をどの順番で処理しても結果は同じになります。
- 出力は以前の逐次処理とビット単位で一致します（6章の回帰確認を参照）。

### 3.3 高解像度出力と xBRZ

エミュレートされるハードウェア（BG0 の 3D、画面キャプチャなど、ゲームが読めるもの）は、常に等倍 256×192 のままです。表示用にだけ、別の高解像度画像を作ります。

```text
（エミュレーション中）
 Gpu::render_3d_frame
   等倍ラスタで描画 → Hires::capture()：描画状態・ポリゴン・頂点・テクスチャを
                                         Arc<Snapshot> にコピー（3D が変わったときだけ）
 compose.rs composite()   3D の画素ごとに「下の層・合成方法」を hd_3d に記録
 output.rs               ラインごとの表示モード・MASTER_BRIGHT・BG0 スクロールを hd_lines に記録

（表示するとき）
 Gpu::hd_frame() → HdFrame   上記すべてと両画面の等倍画像を所有するコピー
 HdFrame::screen(renderer, 上/下, 倍率, xBRZ)
   1. 等倍の画面 → xBRZ（8 バンド並列）または最近傍で拡大
   2. エンジン A の画面なら Renderer がスナップショットを倍率で再描画し、
      3D の画素だけを高解像度の 3D で置き換える（行ごとに並列。
      3D の半透明・BLDY・MASTER_BRIGHT は等倍と同じ計算）
```

- `HdFrame` は所有データだけを持つので、**別スレッドへ送って描画できます**（4.3節）。
- `Gpu::screen_hd()` は `hd_frame()` と `screen()` を続けて呼ぶ簡易版です（egui とテスト用ハーネスが使用）。
- 注意：高解像度では辺が長くなります。補間の `(x*w) << 9` は 32 ビットであふれるため、64 ビットで計算しています（`slope.rs`）。

### 4.2 GUI ごとの実行方式

| GUI | エミュレーションを動かす場所 | 画面の受け渡し |
|---|---|---|
| egui | UI スレッドの `run_frames()`。経過時間から「借り」フレーム数を計算して実行 | 等倍：`draw_screens()` で直接取得。2倍以上：`hd.rs` の HD ワーカーへ `HdFrame` を渡し、完成した画像をテクスチャへ転送 |
| freya | `ds_common::EmuThread` | `Shared::frame_since()` で RGBA を取得 |
| Tauri | `ds_common::EmuThread` | コマンド `get_frame` で RGBA をバイナリのまま React に返す |

### 4.3 エミュレータスレッドと HD ワーカー

```text
 エミュレータスレッド（emulate）              HD ワーカースレッド（hd_worker）
 ┌──────────────────────────┐
 │ キー・タッチ・チートを反映 │
 │ emu.run()                 │
 │ 音声 → TimeStretch → 出力 │
 │ 等倍：両画面 → RGBA → 共有 │
 │ 2倍以上：hd_frame()        │──try_send──▶ HdFrame::screen() ×2
 │   （約 0.1ms のコピー）    │  (待ち合わせ    xBRZ・高解像度 3D
 │ 次のフレーム時刻まで待つ   │   チャネル)     → RGBA → Shared::frame
 └──────────────────────────┘
```

- チャネルは容量 0（待ち合わせ）です。ワーカーが空いているときだけジョブが渡り、忙しければそのフレームは**表示しない**だけです。エミュレーションと音声は遅れません。
- 一時停止中のコマ送りは、待ってでも必ず表示します。
- 1倍より速いときは、フロントエンドがまだ取りに来ていないフレームは作りません（見られないフレームを拡大しても無駄なため）。
- フレームの時刻合わせは約 59.83fps です。大きく遅れた場合は、取り戻そうとせず基準をリセットします。
- egui も同じ仕組みです（`gui/egui/src/hd.rs`）。UI スレッドは `hd_frame()` を渡すだけで、完成した画像は次の描画で受け取ります。ワーカーは完成時に `request_repaint()` を呼びます。

## 5. 音声

### 5.1 出力（`audio.rs`）

SPU の出力（約 32728 Hz、ステレオ）を、出力デバイスのレートへ線形補間で変換して再生します。

- エミュレータは1フレーム分ずつまとめて音を出し、デバイスは連続して消費します。そのため、キューに約 70ms 分たまってから再生を始めます（途切れた後も同じ）。
- **動的レート制御：** キューの量が目標から外れたら、変換比を最大 ±0.5% 調整します。エミュレータの時計とサウンドカードの時計は完全には一致しないためです。
- 目標の 3 倍を超えたときだけ古い音を捨てます。
- `cpal` のストリームは専用スレッドで保持します（Windows の COM 初期化が UI スレッドとぶつかるため）。

### 5.2 倍速時のテンポ変換（`speed.rs`）

倍速や 0.5 倍のとき、**音の高さを変えずにテンポだけ**を変えます（melonDS と同じ聞こえ方）。

```text
 1フレームのサンプル ─▶ TimeStretch::process(ratio) ─▶ AudioOutput::push
                               ▲
        SpeedMeter::tick() ── 実際に出ている速度（約 0.5 秒で平滑化）
        stretch_ratio(設定速度, 実測) = 実測を [0.25, 設定速度] に制限
```

**方式：WSOLA（波形の似た位置で重ね合わせる方式）**

```text
 入力  |--グレイン k--|               名目上の開始位置は HOP×ratio ずつ進む。
               |--グレイン k+1--|     実際の開始は ±SEEK の範囲で、前の続きに
                                      最も似た位置（正規化相互相関）を選ぶ
 出力  |--k--|xx|--k+1--|xx|          xx = OVERLAP 分をクロスフェード
```

| 定数 | 値 | 時間（32728Hz） |
|---|---|---|
| `GRAIN` | 1200 | 約 37ms |
| `OVERLAP` | 240 | 約 7ms |
| `SEEK` | 300 | 約 9ms |
| `HOP` | 960 | 出力側の1グレイン分 |

設計上の判断：

- **以前の方式との違い：** 以前は1フレームごとにサンプルを間引いて（または水増しして）いました。この方式では倍速で音が高くなり、エミュレーションが目標速度に届かないときは「高いだけで速くない」音になっていました。
- **フレームをまたいで状態を持つ：** 1フレーム（約 547 サンプル、17ms）はグレインより短いからです。フレームごとに独立して処理すると、60Hz のブザー音が出ます。
- **比率は設定値ではなく実測値：** 高解像度などで重く 2 倍に届かないとき、設定値の 2 倍で縮めると音が足りなくなって途切れます。実測を使えば、出力される音の長さが実時間と一致します。
- **1 倍はそのまま通す：** 処理による遅延や音質の変化を避けるためです。速度を変えたとき、一時停止したとき、停止したときは、状態をリセットします。
- **リミッタ解除（早送り）中は無音：** 従来どおりです。

egui では1回の描画で複数フレームを実行します。そのため実行したフレーム数を `SpeedMeter::tick(ran)` に渡し、実時間あたりの速度を測ります。

## 6. 品質確認の方法

| 確認 | 方法 |
|---|---|
| 単体テスト | `cargo test --release -p ds_gpu -p ds_common`（テンポ変換：2倍・0.5倍で音程が ±3% 以内、出力長が入力÷比率） |
| 実 ROM テスト | `cargo test --release -p ds_common -- --ignored`（エミュレータスレッドの動作、一時停止、速度と解像度） |
| 描画の回帰 | `core/system/examples/headless.rs`（git 管理外）で、3D のタイトル画面と 3D のステージ紹介を、等倍・2倍・3倍 xBRZ・4倍 xBRZ で PNG に出力し、変更前のビルドと md5 で比較する |
| 速度計測 | ハーネスの `HDBENCH=<倍率>[:x]` で、毎フレームの `run()` と高解像度処理の時間を 300 フレーム平均で表示 |

### 6.1 高解像度処理の計測結果（参考）

3D のタイトル画面（約 620 ポリゴン）、4倍 + xBRZ、16 スレッド環境で、両画面の拡大にかかった時間（300 フレーム平均）。同じ負荷状態で、変更前のビルドと比べています。

| | 変更前 | 変更後 |
|---|---|---|
| 高解像度処理（両画面） | 23.9 ms | 11.8 ms |
| エミュレーション側の負担（全 GUI） | 上記すべて | `hd_frame()` のコピー 約 0.1 ms |

主な改善点：3D ラスタの消去・コピー・final pass のバンド内並列化、バンド数の増加、3D 合成の行並列化、xBRZ のバンド数 4→8、RGBA 変換の単純化、HD 処理の別スレッド化。

## 7. 既知の制約と今後の課題

- 拡大処理（4倍 + xBRZ で約 12ms）が 1 フレームの時間より長くなる環境では、**表示**の更新が 60 回/秒を下回ります。その場合もゲームの速度と音は落ちません。
- **Tauri** は拡大後の RGBA（4倍で約 6MB/フレーム）を IPC で React に送ります。高倍率では、この転送も表示の上限になり得ます。
- テンポ変換は、ゲーム音楽のような信号で破綻しにくい設定です。ただし、極端な速度（4倍）ではグレインのつなぎ目が聞こえることがあります。
